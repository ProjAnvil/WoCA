- 用户新要求：个人开发者用**一个企业版 compose 文件**跑通 EE 沙箱，并且**至少在一台 container 内完成沙箱调用**。用户指定直接写进已有的 `deploy/selfhosted/docker-compose.full.yml`，不新建 compose 文件。
- 用户确认：完整 EE 链 + demo 容器形态；用脚本模型（无需模型 key）。
- 关键代码事实（已核对）：
  - `e2e/sandboxlab/docker-compose.yml` 是现成最小栈（pg、nacos、nacos-init、server、config、worker、fakesandbox、fakemodel、client）。租户 key 在 server 的 `:8090/api/tenant/users` 铸造，run 用 `POST /api/runs` + Bearer key。
  - worker 启动时调 `agentbuild.BuildAgent`，`config.BuildModel` 在 provider 为空时直接报错（`unknown provider`）。所以**模型设置必须先于 worker 存在**，开发者路径必须分阶段启动。
  - 企业版 compose 的 nacos-init 只发空 settings pack；server/worker 之间**没有共享工作区卷**（本次新增 `woca-workspaces` 卷修掉）。
  - 企业版防火墙把五个区两两 DROP，跨区只能靠双网卡服务在共享腿上通信。demo 容器需同时挂 `woca-app` 和 `woca-infra`。

## 架构收敛：server 编排 + worker 做沙箱宿主（2026-10-25 下午）

用户提出微服务划分有问题，并逐步确认了新架构：
- **worker 不是沙箱**。worker 是 woca 自己的编排容器；真正执行命令的是 OpenShell gateway 用 Docker socket 拉起的沙箱容器，绑定宿主而非 worker。
- **共享工作区不是沙箱调用必需的**。它只解决 server 文件树（`internal/server/sessions.go` 的 `workspaceForRequest` + `workspace.go:53` 遍历 server 自己文件系统）和跨 worker 可见性。
- **新划分**：server = 用户入口 + 编排 agent 循环 + 授权；worker = 沙箱宿主 + 文件服务，磁盘是 workspace 代码权威；worker-proxy = 流控 + 路由 + 转发（双网卡 app+exec）；沙箱实现走 woca 抽象（provider 注册表 + contract v2），workspace 不记后端。
- **两条执行路径合并**：个人版 = server 编排 + 本地 executor；企业版 = server 编排 + 远程 executor。接缝就是 `runexec.WithRunExecutor`。
- **每节点一套 OpenShell**：gateway 在哪台宿主，沙箱就在哪台，代码权威也必须在那台。
- **代码事实**：`server.Config.RunLedger` 已存在，SSE 从 PG `run_events` 回放，server 侧有租约对账器；config 台的 verify 现在在 configsvc 进程里建沙箱（`handlers_sandboxes_verify.go` 的 `providers.New`），新架构下必须改成经 proxy 打到 worker。
- **安全问题**：`/api/workspace` 的 `?workspace=` 与 run 请求里的 workspace 路径都没有根目录校验，企业版 server 是共享服务，需要关进配置根目录。
- 已画出两张图：整体角色拓扑、执行节点物理结构（exec 区新增 172.28.40.0/24，只有 gateway 挂 docker.sock）。等用户确认后重写 spec。

## 角色命名与 OpenShell 三件套（2026-10-25 下午续）

- **命名敲定**：server → `woca-scheduler`，worker → `woca-executor`，proxy → `executor-proxy`（流控 + 路由 + 转发）。
- **OpenShell 一个沙箱是三件套**：workload 容器（跑 agent，network=none）+ supervisor 容器（独立容器，策略/凭据/出口代理）+ gateway（控制面：生命周期、策略下发、凭据、prover、服务路由、状态库）。
  - 证据：`docs/about/architecture.mdx` "provisions a workload **and a separate supervisor**"；`crates/openshell-driver-docker/src/lib.rs` 常量 `SANDBOX_BINARY_PATH=/.openshell/runtime/openshell-sandbox`、`SUPERVISOR_IMAGE_CONTROL_BINARY_PATH=/openshell-supervisor`、`SUPERVISOR_UID/GID=65534`；配置注释 "Networking mode for the supervisor only. Workloads always use network=none"。
- **只跑 workload 容器不行**：没有 supervisor 就没人代理出口、解析 DNS、接命令通道；没有 gateway 就没有生命周期、策略、凭据、服务暴露。
- **把 executor 当成跑 agent 的容器更不行**：边界靠 workload 与 supervisor 分离，agent 若与受信侧同容器就能读模型 key 和证书。executor 必须在边界外。
- **能省的是 adapter**：它是"Executor 语义 → OpenShell"的映射层，应做成 executor 内部模块，不单独跑服务（少一个容器、少一跳、少一份凭据分发）。
- executor 节点是受信节点：持 OpenShell gateway 的客户端证书，gateway 持 docker.sock，executor 自身不挂 socket。

## 沙箱方案重新选型（2026-10-25 傍晚）

OpenShell 结论：不是坏方案，是太重（三件套 + 每节点控制面 + 策略体系），与 woca 想要的“一个 compose 文件、容器内跑通、沙箱可插拔”成本收益不匹配。

2026 年新开源的一批（已核实）：
- **OpenSandbox**（alibaba，Apache-2.0，Linux Foundation 项目，2026-03）：分层与 woca 目标几乎同构。`specs/sandbox-lifecycle.yml` 等 OpenAPI（base path `/v1`）定义生命周期+执行；FastAPI 的 `opensandbox-server` 做控制面（API key 认证）；`runtime.type` 取 `docker`（本地/单机）或 `kubernetes`；K8s 模式接 `kubernetes-sigs/agent-sandbox` 与 BatchSandbox，另有 FastSandbox（Firecracker，按 `fsb-` ID 前缀路由）；沙箱内是 **Go 写的 `execd`**（SSE shell、后台进程、持久 bash session、PTY、文件操作、进程隔离 session、Jupyter）；出口靠每沙箱 egress sidecar + DNS/nftables，凭据靠 credential vault 在沙箱外注入；服务访问走 server proxying + K8s ingress gateway。Go SDK：`github.com/alibaba/OpenSandbox/sdks/sandbox/go`。CLI `osb`，MCP server `opensandbox-mcp`。
- **Perplexity SPACE**（2026-10-15，Apache-2.0，Rust + Firecracker，E2B 兼容包装）：红队 108 次越界 0 成功，但曾有 54 次部分网络运行中 11 次绕过出口策略，后用 nftables 源地址校验 + TLS 终止修掉。要 Linux x86_64 + KVM + btrfs + Docker，本地跑要 Kind。
- **Tencent CubeSandbox**（2026-04，Apache-2.0，RustVMM + KVM）：CubeAPI/CubeMaster/Cubelet/CubeVS（eBPF 网络策略）/CubeEgress（域名过滤+凭据注入+审计），E2B 兼容，Helm + 单机脚本，v0.5 起支持 ARM64。要 KVM。
- **Moonshot AgentENV**（2026-07，MIT，Firecracker + envd + E2B 兼容）：偏 RL 训练，要内核 6.8+ 与 /dev/kvm。
- **Hyperlight**（Apache-2.0，CNCF）：嵌入式 VMM 库，guest 无内核，只能跑专用 Rust/C 函数，**不能跑 agent 工具链，排除**。相关 hyperlight-unikraft / hyperlight-sandbox 尚早。
- 仍有效：E2B Embed（两个文件一条命令，但官方自述是评估包形态）、microsandbox（Apache-2.0，Go SDK，已在 woca 枚举）、agent-sandbox（SIG Apps）、gVisor/Kata 当 runtime。

**硬约束**：所有 microVM 方案都要 KVM。woca 现有 AWS 部署是 t4g.medium，无嵌套虚拟化，microVM 跑不了。gVisor 不需要 KVM，Kata 需要 virt-capable 节点。默认档必须是容器级隔离。

**推荐**：默认档用 OpenSandbox Docker runtime（gVisor 隔离），企业 K8s 档用 agent-sandbox + RuntimeClass（高危池 Kata），硬件级档留给有 KVM 宿主的场景（如 CubeSandbox / SPACE）。三者都落在 woca 的 provider 抽象里，workspace 不记后端。
