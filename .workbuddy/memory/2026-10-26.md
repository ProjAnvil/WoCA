## proxy 承担调度与队列（2026-10-26 中午）

用户决策：
- **工作区 ID 由 proxy 生成**。用户问这是否可以理解成"workspace 的实际内部会话 ID"。答案：它是执行环境的身份，不是聊天 session 的 ID。多个聊天 session 共享同一工作区时，session ID 不同，workspace ID 相同。
- **executor 可横向扩容**，每个 executor 的同时 run 数与当前负载由 proxy 控制。
- **个人版 executor 只在本地，不接入这条路径**。个人版继续本地执行。

spec 修订（提交 `bb61342`）：

## 遗留容器的语义澄清（2026-10-26 中午）

用户问"遗留容器"指什么。澄清并写入 spec（提交 `ffbfc72`）：
- 遗留容器 = 宿主上的**真实沙箱容器**，不是 executor 内部的虚拟容器。
- 三层：executor 容器（woca 角色，长期运行）／沙箱容器（宿主真实容器，每个 run 一个）／命令进程（容器内进程，单次 exec）。
- **执行命令不新建容器**：所有工具调用走 runtime exec 接口在同一个沙箱容器里起进程。
- 遗留来源：executor 崩、调度器崩、调用方断连、宿主异常重启。
- 清理靠标签识别：`woca.sandbox=1`、`woca.workspace=<id>`、`woca.run=<id>`、`woca.executor=<id>`，只删不在活跃集合里的。容器内残留进程随容器删除一起消失。

## 宿主 / executor / 沙箱 三者关系（2026-10-26 中午）

用户问"虚拟化的宿主机是不是 executor"。澄清并写入 spec（提交 `44f2228`）：
- 宿主 = 跑 container runtime 的机器（物理机 / 云主机 / VM）。executor 不是宿主。
- executor 容器与沙箱容器是**兄弟容器**，同一个宿主、同一个内核。
- 隔离由 container runtime 提供（runc / runsc / kata），不由 executor 提供。
- executor 持有 runtime 全量 API 权限，比沙箱更靠近信任边界 → 所在节点必须完全受信。
- Kata 模式下沙箱多一层轻量虚拟机，首期不做。

## 审计：executor 能否与 scheduler 合并（2026-10-26 中午）

用户提出合并 executor 与 scheduler。审计结论：
- **技术上可行，但收益不在省一个容器，而在工作区目录放哪。** 两件事被绑在一起。
- 收益：少一个容器；**文件树代码不用改**（`internal/server/workspace.go` 走宿主文件系统 `os.ReadDir`/`os.Stat`，工作区在 scheduler 本地就现成可用）；少一跳。
- 代价：API 面拿到 runtime 全量权限（远端租户的 HTTP 请求进有 socket 的进程）；慢沙箱占用 API 进程资源；扩缩容绑死（副本数=节点数）；工作区跟着 API 副本走。
- **关键发现**：保持分离但把工作区目录放**共享卷**（scheduler 与 executor 挂同一路径），文件树同样不用改，工作区还不绑 executor，可迁移。所以"文件树要不要改"和"要不要合并"不是同一个问题。
- 用户决策：**保持分离 + 共享卷**。
- spec 修订（提交 `cf850ea`）：新增 `woca-workspaces` 卷挂 scheduler 与 executor；§5.4 改为"工作区文件由 scheduler 提供"，删掉 executor 的文件服务；文件树路径限制在卷根内并按租户过滤（顺带修掉现在 `?workspace=/etc` 的路径越权）；"新 executor 只接新工作区"的硬约束取消，改绑定记录即可迁移。
