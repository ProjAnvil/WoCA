## woca Web Search 能力深度调研（产出 docs/websearch-research.md）

用 superpowers 方法论的「先规格后实现」阶段，派 4 个并行调研子代理 + 自己做一手源码核实，
产出 `docs/websearch-research.md`（约 860 行）。未写任何实现代码——这是规格阶段，等用户拍板。

### 回答用户的核心问题：MCP 还是内置 tool calling？

**是伪二选一。** 真实结构是三层，第 2 层（客户端内置）是主力，MCP 只是可替换后端之一：

- 第 1 层 模型服务端（Claude/Codex/Gemini 的 hosted search）——**不能依赖**，绑死厂商，Bedrock 没有
- 第 2 层 客户端内置工具——**必需品**，所有严肃 harness 都自己实现
- 第 3 层 MCP——可替换 provider 来源，不是替代品

**收敛方向**：`Twigpine/zero` 的 `searchBackend` 接口 + `anomalyco/opencode` 的 provider 注册表
（5 个 provider、冷却表、429 故障转移、会话亲和、凭据链）。

### 最关键的发现（两条）

1. **G2：woca 无法区分「被拦」和「搜不到」。** DDG 返回 challenge 页时解析出 0 条，
   向模型谎报 `No results found` → 模型断定「信息不存在」→ 编造或死循环改写 query。
   社区 issue jcode #1765 记录过同一失败模式。**P0，最先修。**

2. **DDG 在 2026 年按 IP 信誉拦截，数据中心 IP 确定性失败（HTTP 202 + JS challenge），换 UA 无效。**
   本机（住宅 IP）实测跑通，但 woca 的生产形态（企业 worker/CI/容器）大概率是数据中心 IP。
   **本机跑通不构成验证。** → DDG 只能当降级项，不能当默认。

### woca 现状盘点出的差距（G1–G10）

| 编号 | 要点 |
|---|---|
| G1 | 无 provider 抽象，`--search-api` 是全局单点替换，无回退/冷却 |
| G2 | 无法区分被拦与搜不到（最严重） |
| G3 | UA 固定 `woca/0.1`（但换 UA 不解决根本问题） |
| G4 | 无请求节流 |
| G5 | 正则解析（对比 Crush 用 `x/net/html` 真 DOM） |
| G6 | WebFetch 只去标签，无 Markdown/正文抽取/落盘 |
| G6a | **`maxWebChars = 20000` 名不副实**：Go `len(string)` 返回字节，中文 3 字节/字只拿到约 6,667 字；且 `out[:20000]` 按字节切片**会切坏汉字** |
| G7 | `ValidateURL` 只校验 hostname 不解析 IP，`SSRFSafeTransport` 存在但 `fetchHTTP` 未用 → DNS rebinding 可绕过 |
| G8 | 无 managed/企业配置层（MCP 与 skills 都有，搜索是唯一缺口） |
| G9 | Web 工具不经 executor，恒定跑宿主进程 |
| G10 | 结果无元数据（发布时间） |

**实测**：12 个常见文档页去标签后 text 中位数 **54,949B**，50% 超过 50KB。
woca 现在截到 20,000B → **多数英文文档页被裁到只剩约 36%**。

### 依赖决策（实测结论，不是估计）

**goquery 不是新依赖**：`v1.10.0` 早已在模块图（经 `langchain-golang/core/documentloaders` 传入），
go.sum 有完整 `h1:` zip 校验和、源码已在 GOMODCACHE，`GOPROXY=off go run` 直接跑通。
我们只是把它从 indirect 提为 direct，**版本未升 → 供应链零变化**。
构建图增量 4 包：goquery / cascadia / x/net/html / x/net/html/atom；
go.sum 多出的 34 行**全是 `/go.mod` 行**（MVS 图遍历产物），没有 `h1:` 行 = 没有新下载代码。
`golang.org/x/time`（rate）与 `golang.org/x/net` 本就在 go.mod 里带 `h1:`，可直接用。
→ **结论：用 goquery。自研 HTML 解析只有两条路：继续正则（就是要修的 G5）或 x/net/html 手写树遍历（约 80 行）。**

**CI 有强制依赖基线**：`ci/deps-personal.txt` 由 `make check-deps` diff 校验。
本次 +8 行 = 本分支 6 行 + **main 上既有的 2 行漂移**（`core/stores`、`internal/runexec`，main 上就已可达但基线未重生成）。

### 关键设计修正（读代码后比调研文档更精确）

调研说「DDG 挑战页谎报 No results」。实测读 `web.go`：**非 200 时 `fetchHTTP` 本来就返回错误**（只是报裸 `HTTP 202`，没用）。
真正说谎的是 **HTTP 200 + 挑战页**（无 result 锚点 → 0 条 → "No results found."）。
所以 P0 是两半：① 200+0 条+命中标记 → ErrRateLimited；② 202/429/503 → ErrRateLimited（不是裸状态码）。

反爬标记必须是**短语不是单词**（`anomaly-modal` 而非 `anomaly`）——搜 "anomaly detection" 的正文里本就带 "anomaly"，
用单词会把正常空结果误报成限流。

**其他要点**：`Retry-After` 上限 10 分钟（否则恶意值可永久停掉某后端，把流量赶到指定去处）；
故障转移**只认限流**（网络错/401/非503的5xx 直接返回，否则把配置错误伪装成抖动）；
域名过滤**先筛后装载**；`--search-api` 独占（悄然回落 DDG = 查询外发）。
